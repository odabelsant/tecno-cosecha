Gestión de Imágenes & Multiformato Fase 15 & 16: Admin & Piloto Fecha: 2026-10-09

🌾 Iteración: Gestión de Imágenes y Carga Multiformato (5 Extensiones)

Soporte de miniaturas en Catálogo, uploader interactivo con validación explícita (JPG, PNG, GIF, SVG, WebP) y vista previa instantánea en Publicar.

1. ANTES

Las tarjetas del catálogo mostraban únicamente atributos de texto plano (título, precio, unidad, ubicación) sin fotografías ni soporte visual representativo. La pantalla de publicación (/publicar) era un formulario prototípico sin campo de subida de archivos ni validación de formatos multimedia, y la base de datos relacional no contemplaba persistencia de imágenes en los lotes de cosecha.

2. CAMBIO

  • Base de Datos y Persistencia: Migración versionada 0007_posts_image_url.sql agregando columna image_url a marketplace_posts. Adaptación de DTOs y servicios en src/modules/publications/service.ts. Endpoints GET y POST en /api/publications.
  • Biblioteca Gráfica de Cultivos: Colección de gráficos vectoriales SVG ligeros (<1KB cada uno) en public/images/crops/ (tomate, zanahoria, habichuela, plátano, mango, cebolla, ají, yuca, batata, aguacate, chinola y default). Sembrado de imágenes en 16 publicaciones con npm run seed:demo.
  • Frontend — Catálogo con Miniaturas (src/app/catalogo/page.tsx): Miniaturas representativas (110x110px) en cada tarjeta con carga diferida y fallback automático inteligente.
  • Frontend — Módulo de Carga Multiformato (src/app/publicar/page.tsx): Zona drag-and-drop con soporte y validación explícita para 5 extensiones estándar de la web (JPEG/JPG, PNG, GIF, SVG, WebP), tarjeta de vista previa instantánea (nombre, tamaño formateado, badge de formato) y opciones para cambiar o eliminar la foto.
  • Pruebas Automatizadas: Nueva suite tests/images.test.ts (67 pruebas pasando en total).

3. DESPUÉS

Los compradores pueden visualizar fotografías representativas de las cosechas directamente en el catálogo, aumentando la confianza comercial. Los productores disponen de un cargador de fotos intuitivo y accesible que valida los 5 formatos web más utilizados, previsualiza la imagen en tiempo real y persiste el lote inmediatamente.

4. EFECTO PARA EL USUARIO

Comprador: Visualización inmediata del producto agrícola antes de comprar o cotizar.

Productor: Facilidad de destacar su lote subiendo fotos desde su celular en formatos estándar (JPG, PNG, GIF, SVG o WebP) con vista previa instantánea.

Evaluador/QA: Pruebas visuales completas tanto con datos sembrados como publicando nuevos lotes con foto.

5. SIN CAMBIOS

Se conservan intactas la paleta canónica (#245C3A, #4D8A62, #C8754D, #F7F5EC, #253129), la navegación móvil fija inferior, el ciclo de cotizaciones inmutables y el panel de auditoría administrativa.

6. LIMITACIONES

Almacenamiento actual en base de datos SQLite y rutas estáticas locales; para despliegues a gran escala se sugiere un bucket S3/R2. Límite sugerido de 8 MB por fotografía para cuidar redes móviles rurales.

7. CÓMO VERIFICARLO

npm test tests/images.test.ts
npm run seed:demo
# Abrir http://localhost:3000/catalogo y http://localhost:3000/publicar

⚖️ 8. DICTAMEN DEL JUEZ DE CALIDAD (PUERTA DE CALIDAD)

VEREDICTO: ACEPTADO

  • Visualización en Catálogo: Cumplida con miniaturas representativas por cultivo y fallbacks.
  • Carga Multiformato: Cumplida con validación para 5 formatos web (JPG, PNG, GIF, SVG, WebP) y vista previa.
  • Persistencia y Semillas: Cumplida. 16 ofertas de venta y 12 demandas de compra activas en el mercado dominicano.
  • Evidencias de QA: 67/67 pruebas pasando (100%), typecheck limpio, linter sin advertencias y verificación en vivo en navegador.

Iteración Anterior: Fases 15 y 16 (Admin, E2E y Piloto)

1. ANTES (Fases 15 & 16)

La plataforma disponía del flujo transaccional y los planes de suscripción (Fases 13 y 14), pero carecía de una interfaz de supervisión administrativa centralizada para moderar usuarios, revisar publicaciones reportadas y otorgar verificaciones de parcela; no existía un registro de auditoría estricto de las intervenciones técnicas; y no se disponía de una suite E2E de validación holística ni de copias de seguridad automáticas en caliente para la base de datos.

2. CAMBIO

El equipo diseñó e implementó los componentes de cierre y endurecimiento de la plataforma:

🛡️ Fase 15: Administración y Auditoría

Panel protegido (/admin) con mínimo privilegio (rol ADMIN). Libro inmutable de auditoría (admin_audit_logs) con actor, entidad, acción y motivo obligatorio. Prohibición estricta de alteración unilateral de pedidos pactados.

🚀 Fase 16: Validación E2E y Piloto

Prueba holística de extremo a extremo (publicación → cotización → pedido → entrega con merma → reseña → disputa → auditoría → respaldo). Módulo de backup en caliente de SQLite y especificación del piloto para el Cibao Central.

Persistencia: Migración versionada 0006_admin_audit_logs.sql y reversión 0006_admin_audit_logs.down.sql.

3. DESPUÉS

Tecno Cosecha cuenta con su arquitectura MVP completa, probada de extremo a extremo, endurecida y lista para pruebas operativas: desde el primer registro hasta la resolución mediada y la copia de seguridad, con 64 pruebas automatizadas pasando y 18 rutas Next.js operativas.

4. EFECTO PARA EL USUARIO

  • Para el Equipo de Soporte y Operaciones: Panel claro con métricas del sistema, herramientas para proteger a la comunidad de estafas y respaldo auditable de cada decisión.
  • Para Agricultores y Compradores: Certeza de que la plataforma está supervisada activamente por humanos y que sus acuerdos no pueden ser alterados arbitrariamente.
  • Para el Propietario del Producto: Hoja de ruta 100% implementada con criterios medibles y plan de piloto estructurado.

5. SIN CAMBIOS

  • No se han integrado cobros con tarjeta ni comisiones bancarias automáticas, en cumplimiento estricto de ADR-004.
  • La paleta visual canónica (#245C3A, #4D8A62, #C8754D, #F7F5EC, #253129) rige de manera consistente toda la aplicación.
  • Todas las migraciones previas (0001 a 0005) continúan 100% íntegras y estables.

6. LIMITACIONES

  • El piloto inicial está restringido a 15 productores y 10 comercios en el Cibao Central para mantener supervisión directa.
  • La resolución de incidencias es administrativa/mediada sin débitos automáticos bancarios.

7. CÓMO VERIFICARLO

# 2. Verificar tipos y compilación de producción
npm run typecheck && npm run lint && npm run build

# 3. Iniciar la aplicación y navegar en http://localhost:3000/
npm run dev

# 4. Abrir la documentación pedagógica
